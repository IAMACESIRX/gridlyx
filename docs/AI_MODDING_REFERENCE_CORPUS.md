# Gridelyx AI modding reference corpus

Status: **canonical human + AI reference architecture**

Gridelyx must give a human developer or AI coding agent nearly the same practical reference surface as a repository that vendors an MDK, Minecraft development runtime and dependency source bundles **without publishing those upstream payloads in Git**.

The model is:

```text
tracked Gridelyx source + version locks + source map + skills
                     |
                     v
         official/authorized resolvers
                     |
                     v
           ignored local reference cache
                     |
          +----------+-----------+
          |                      |
          v                      v
   searchable source/docs     build/runtime cache
          |                      |
          +----------+-----------+
                     v
              human / AI agent
```

Machine-readable source map: [`../platform/reference-sources.json`](../platform/reference-sources.json).

Dependency/tool inventory: [`DEPENDENCIES_AND_TOOLCHAIN.md`](DEPENDENCIES_AND_TOOLCHAIN.md) and [`../platform/toolchain-requirements.json`](../platform/toolchain-requirements.json).

Acquisition policy: [`../vault/manifest.json`](../vault/manifest.json).

## Core rule

The public repository stores:

- Gridelyx-owned source, examples, schemas, skills and documentation;
- exact dependency coordinates and version locks;
- official documentation/source URLs;
- immutable upstream revisions when practical;
- hashes/provenance supplied by upstream providers;
- acquisition/indexing scripts;
- AI routing metadata describing which source to consult for which type of problem.

The public repository does **not** store:

- Minecraft client/server JARs;
- generated/decompiled Minecraft source trees;
- NeoForge installer/runtime JAR copies;
- JDK or Gradle distributions;
- Maven/Gradle caches;
- LWJGL distribution archives/native bundles;
- hydrated upstream repositories;
- third-party source JARs copied out of package caches;
- chunked/renamed versions of any of those payloads.

## Reference hierarchy for AI agents

An AI writing a NeoForge mod should consult sources in this order unless the task requires a lower-level implementation detail:

1. **Gridelyx canonical template and project rules** — [`../templates/neoforge-26.2/`](../templates/neoforge-26.2/), [`../AGENTS.md`](../AGENTS.md), [`../platform/versions.json`](../platform/versions.json).
2. **Pinned NeoForge 26.2 MDK** — exact upstream template shape, Gradle layout, metadata and generated example structure.
3. **Official NeoForged documentation** — API usage and supported patterns for registries, events, data generation, networking, rendering, worldgen, configuration and toolchain behaviour.
4. **NeoForge / ModDevGradle source** — implementation-level questions, lifecycle behaviour and exact toolchain mechanics.
5. **Resolved source/Javadoc artifacts** — ASM, LWJGL, GraalVM, JUnit, ArchUnit and other declared Java libraries.
6. **Locally generated Minecraft development source** — exact vanilla types, signatures and implementation reference for the selected Minecraft version, only when generated by the supported development toolchain and used under applicable Mojang/Minecraft terms.
7. **JDK source/Javadocs** — Java 25 APIs including NIO, Instrumentation, concurrency and FFM/Panama.

Do not answer a version-specific API question from memory when the local/reference source can resolve it.

## Local hydration

### Minimum upstream MDK reference

```bash
python tools/hydrate_references.py --mdk
python tools/build_reference_indexes.py
```

This creates ignored reference state under `.reference-cache/`.

### AI/open-source corpus

```bash
python tools/hydrate_ai_references.py --core
python tools/build_reference_indexes.py --corpus
```

`--core` is intended to hydrate high-value official source/documentation repositories such as the MDK, NeoForged documentation and ModDevGradle into ignored local directories. Additional open-source source trees can be selected explicitly.

The hydration step records the actual resolved Git commit for every non-immutable upstream checkout in `.reference-cache/index/reference-provenance.json` so an AI response can identify which source revision informed it.

### Java/Maven dependency sources

The canonical Gradle template already requests IDE source and Javadoc downloads:

```gradle
idea {
    module { downloadSources = true; downloadJavadoc = true }
}
```

Run the normal dependency resolution/build when an empty cache is being populated:

```bash
cd templates/neoforge-26.2
gradle --no-daemon --refresh-dependencies help
```

Gradle/ModDevGradle then owns the binary/source/Javadoc cache. Do not copy those caches into the repository.

## Minecraft development source rule

NeoForge's supported development workflow resolves Minecraft and produces a development-friendly environment locally. This is the correct way to answer exact Minecraft implementation questions.

For Gridelyx AI use:

- generate/resolve the target through ModDevGradle;
- allow the IDE/toolchain to attach the generated Minecraft sources;
- point a local RAG/indexer at those generated sources if the user's terms and local environment permit it;
- attach version, mapping and provenance metadata to every indexed chunk;
- keep the resulting index/source outside Git;
- do not publish generated/decompiled Minecraft source as Gridelyx documentation or a public training corpus;
- do not assume that permission to inspect locally equals permission to redistribute or use the material in a public model-training dataset.

For public AI skills, prefer distilled Gridelyx-authored explanations and exact source pointers. For implementation lookup, use local retrieval against the developer's resolved environment.

## AI skill construction

A modding skill should encode **procedure and routing**, not copied upstream source.

Recommended skill structure:

```text
skill
  identity:
    minecraft: 26.2
    neoforge: 26.2.0.67
    moddevgradle: 2.0.144
    java: 25
  read_first:
    - templates/neoforge-26.2/build.gradle
    - templates/neoforge-26.2/gradle.properties
    - platform/reference-sources.json
  topic_routes:
    registries: NeoForged docs -> NeoForge source -> local Minecraft source
    networking: NeoForged docs -> NeoForge source
    rendering: NeoForged docs -> NeoForge source -> LWJGL -> local Minecraft source
    worldgen: NeoForged docs -> codec/datagen examples -> local Minecraft source
    bytecode: Gridelyx advanced runtime -> ASM source/docs -> exact target descriptors
  validation:
    - compile
    - formatting/checkstyle
    - unit/architecture tests
    - GameTest/runtime evidence where applicable
```

The AI should always identify whether its answer came from a **pinned fact**, **official current documentation**, **source inspection**, or an **assumption requiring runtime validation**.

## Index format

Local indexing should produce `.reference-cache/index/reference-corpus.jsonl` with one record per source/document chunk. At minimum each record should preserve:

```json
{
  "source_id": "neoforge-documentation",
  "version": "target-current",
  "resolved_revision": "<git sha when applicable>",
  "path": "docs/...",
  "sha256": "<file or chunk digest>",
  "roles": ["networking"],
  "redistribution": "local-reference-only",
  "content_location": ".reference-cache/..."
}
```

The index itself stays local because it may reveal or contain material derived from locally hydrated sources. The public repository contains only the schema/routing rules and official pointers.

## Updating a dependency or target

When Minecraft, NeoForge, ModDevGradle, Java, Gradle or a major library changes:

1. update [`../platform/versions.json`](../platform/versions.json) and the canonical template;
2. update [`../platform/toolchain-requirements.json`](../platform/toolchain-requirements.json);
3. update [`../vault/manifest.json`](../vault/manifest.json) if acquisition semantics changed;
4. update [`../platform/reference-sources.json`](../platform/reference-sources.json) and any immutable upstream revision;
5. refresh the local corpus and provenance file;
6. rebuild/reference-index the hydrated sources;
7. run the clean-cache public build;
8. run both current-tree and reachable-history redistribution guards;
9. validate code examples against the new target before teaching the AI that the old API still applies.

## Publication safety

Current-tree guard: [`../tools/redistribution_guard.py`](../tools/redistribution_guard.py).

```bash
python tools/redistribution_guard.py
```

Reachable-history guard: [`../tools/history_redistribution_guard.py`](../tools/history_redistribution_guard.py).

```bash
python tools/history_redistribution_guard.py
```

The GitHub workflow additionally fetches public branch/tag refs and GitHub pull-request head refs before running the history guard. A repository should not be made public while that audit reports a prohibited payload.

GitHub may retain unreachable objects or old pull-request/cache views after a force-push. A clean reachable history prevents normal branch/tag cloning from retrieving those objects, but a previously known obsolete SHA can remain accessible until GitHub garbage-collects it or Support removes it. If a prohibited binary was ever actually pushed, treat server-side purge as a separate publication checklist item rather than assuming a history rewrite instantly destroys every GitHub-side copy.
